# 승인 대상의 원래 평가를 소유 저장소에서 조회

[English](workflow-2-owned-approval-subject.md) | [한국어](workflow-2-owned-approval-subject.ko.md)

Workflow 2 체크포인트 4는 아직 완료되지 않았습니다. 이 내부 조회기는 원래 요청에서
소유 작업을 찾고, 기존의 봉인된 스냅샷·결과 검증을 승인 대상 조회에 연결합니다.

`readOwnedReleaseApprovalSubject`는 정확한 범위와 요청 참조로 `findJobForRequest`를
먼저 호출합니다. 실제 저장소가 반환한 작업 신원으로 후속 조회를 수행하고, 요청자가
제시한 작업 ID·후보·정책·요청·스냅샷·결과가 그 원본과 같은지 대조합니다. 누락·대기
중인 작업이나 조회 시각 이후에 완료된 작업은 스냅샷 페이지를 읽기 전에 거부합니다.

스냅샷 루트와 모든 순서화된 페이지를 검증하고, 원래 시도·펜스·시각·결과를 기존 소유
검증기로 재계산합니다. 규칙은 원래 정책과 결과 양쪽에 있어야 합니다. 최신 결과나
임의 그래프·작업자·일부 페이지만으로 대체할 수 없습니다. 원래 `approval_required`의
`approval_not_evaluated` 상태는 그대로 보존됩니다.

모든 읽기 시도·반환 자료·반복 메타데이터 검증은 서버가 소유한 단일 누적 예산에
포함됩니다. 읽기나 예산 실패를 잡아도 전체 조회는 실패 상태를 유지합니다. 네이티브
구성에서는 실제 정규화된 DB 관측도 같은 예산에 포함해야 합니다. 포트는 기존의 읽기
메서드만 제공하며 SQL·클라이언트·내용/키·발행 기능을 노출하지 않습니다.

반환 경계는 `original_evaluation_subject_only`입니다. 선택 참조의 형식은 검사하지만
현재 선택의 실제 권한은 이 조회기에서 검증하지 않습니다. 현재 정책·검토자 권한,
근거/통제 내용, 비루트 평가자 출처, 실제 사용자 인증과 유지 중인 네이티브 발행
가드는 별도의 소유 서비스가 검증해야 합니다. 이 과거 조회 결과로 발행 권한을
대신하거나, 일반 승인과 알려진 위반의 예외를 섞을 수 없습니다.

테스트는 실제 메모리 저장소의 완료된 작업·지불된 규칙 예약·봉인 페이지·발행된
결과를 사용합니다. 원래 네이티브 입력을 보존한 세 테넌트에서 작업·스냅샷·결과 ID가
충돌하는 경우, 잘못된 참조·범위·시각·페이지·결과와 누적 예산 경계를 검증합니다.
실제 승인 발행·네이티브 가드/복구·결과 전 입력 계획·결정·API/SDK·기여자 통합·독립
종료 감사가 남아 있으며, 이후 체크포인트 5–7과 측정에 따른 5단계를 진행합니다.
