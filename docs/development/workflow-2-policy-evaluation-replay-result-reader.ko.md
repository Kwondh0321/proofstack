# 정책 평가용 재현 결과 읽기

[English](workflow-2-policy-evaluation-replay-result-reader.md) |
[한국어](workflow-2-policy-evaluation-replay-result-reader.ko.md)

상태: 기록 수준 수집 구현. 재귀 수집, 보호된 스냅샷, 규칙 평가, 영속 정책 워커와
체크포인트 종료 승인은 아직 완료되지 않았습니다.

[재현 결과 읽기](../../packages/replay/src/policy-evaluation-replay-result-reader.ts)는 기존
[정의 읽기](workflow-2-policy-evaluation-definition-readers.ko.md)에 `replay_result` 출처를
추가합니다. 계획이 존재한다는 사실과 실행이 성공했다는 기록을 구분합니다. 정확한 작업의
보관 이력을 읽고 최종 성공 시도가 요청된 전체 결과 참조와 일치하는지 검증합니다.
새 재현 작업을 실행하거나 정책 결과를 발행하지 않습니다.

## 권한·참조·시각 경계

`readPolicyEvaluationReplayResult`는 이미 인가된 범위, 정확한 출처 참조, 명시적 의미 시각
`evaluationTime`, 유한한 수집 한도와 읽기 전용 `findJob` 메서드를 받습니다. 입력을 검사하고
복사한 뒤 저장소를 한 번 호출합니다. 최신 결과 검색, 유리한 시도 선택, 네트워크 검색,
다른 범위나 결과로의 대체는 하지 않습니다.

전체 응답에 `ReplayJobSnapshotSchema`를 적용해 작업·시도 일관성, 연속 이력, 범위와 fence,
예산 정산, 취소 요청·확인 관계를 검사합니다. 이전 시도는 교체 시점까지 종료되어야 합니다.
결과는 최종·최신 성공 시도여야 하며 대기, 실행 중, 실패, 시간 초과, 취소, 예산 소진 상태를
성공으로 해석하지 않습니다. 다음 참조를 모두 비교합니다.

- 작업·시도 ID와 테넌트·프로젝트·환경 범위
- 계획 ID·버전 ID·정의 다이제스트
- 결과 파일 ID·SHA-256·바이트 수·미디어 유형·분류
- 대상 ID·릴리스 ID·정의 다이제스트·어댑터 및 워커 프로토콜의 중첩 정보
- 성공 종료 상태·완료 코드와 정확한 시도 종료 시각

`completedAt`은 시도의 `endedAt`이며 작업 종료 기록의 `committedAt`이 아닙니다. 두 기록
시각이 달라도 혼동하지 않습니다. 동일 시각의 오프셋·소수초 표기는 지원 정밀도를 보존해
비교하고, 반환 기록 및 해시에 들어가는 원본 시각 표기는 변경하지 않습니다.

작업 생성·시작·종료 확정, 모든 시도 시작·종료, 예산 예약·정산, 취소 요청·확인, 실행·사용량
관찰 시각이 모두 `evaluationTime` 이하여야 합니다. 미래 기록을 버리고 유리한 과거 화면을
만들지 않습니다. 취소 의도와 성공 종료는 공존할 수 없으며 공통 스키마가 결과·시각 검사 전에
이 모순을 거부합니다. 상위 수집 경계의 인증·인가는 별도이며, TypeScript 메서드 제한만으로 DB
권한이 줄어드는 것은 아닙니다. 정책 워커에 재현 제어·실행 자격 증명을 공유하면 안 됩니다.

## 관찰과 유한한 수집 한도

| 상황 | 결과 |
| --- | --- |
| 정확한 조회가 `null` 반환 | `missing`, 기록 없음 |
| 스키마·내부 이력 오류 | `unavailable` / `record_invalid`, 기록 없음 |
| 유효한 기록이지만 정확한 성공 참조 불일치 | `unavailable` / `reference_mismatch`, 기록 없음 |
| 평가 시각 이후의 기록 시각 존재 | `unavailable` / `not_yet_available`, 기록 없음 |
| 기록 검사 통과 | `verified`, 전체 canonical 기록 SHA-256 및 독립 사본 |
| 입력 오류 | I/O 전에 `policy_evaluation_replay_result_read_input_invalid` |
| 수집 한도 초과 | `policy_evaluation_replay_result_read_limit_exceeded`, 운영 오류 |
| 저장소 실패·예상 밖 검증 예외 | 원래 예외 전파 |

`limits.maximumRecords`와 `limits.maximumRecordBytes`는 상위 수집기의 남은 예산에서
지정합니다. 기존 요청 contract의 절대 상한인 기록 100,000개·64 MiB를 넘길 수 없습니다.
기록 수는 작업 루트, 모든 시도·예산 원장·취소 확인·관찰 행과 존재하는 취소 요청을 합산합니다.
종료 기록은 작업 루트 안에 포함됩니다. 배열 원소를 파싱하기 전에 개수 제한을 확인하며
초과 이력을 잘라내지 않습니다. 바이트 한도는 모든 이력·시각을 포함한 canonical UTF-8 JSON
크기입니다. 정확한 한도는 허용하고 한도 초과는 부재나 정책 판정으로 바꾸지 않습니다.

엄격한 스키마 검증 **후에만** 선택 필드의 `undefined`를 JSON의 필드 부재로 정규화합니다.
이는 기존 메모리 상태 전이와 DB·HTTP 표현을 맞추기 위한 것으로, 알 수 없는 필드는 값이
`undefined`여도 정규화 전에 거부합니다. 결과 참조만이 아니라 전체 기록을 해시하므로
발행 메타데이터나 자식 관찰만 변경되어도 해시가 달라집니다.

이 한도는 이미 저장소에서 반환된 값의 수용 한도입니다. DB 스트리밍, 전체 그래프의 누적 예산,
시간 제한, 취소를 구현했다는 뜻은 아닙니다. 상위 수집기는 읽기 단계의 자원 제한, 전체
I/O·개수·바이트·시간 계산과 일관성 검사를 추가해야 하며, 한도를 넘겼다고 다른 결과를 고르면
안 됩니다.

## 검증과 남은 범위

메모리 상태 전이와 PostgreSQL 완료 함수를 교차 점검해 기존 읽기 스키마의 불일치를 찾았습니다.
취소 의도가 보관됐는데 작업이 계속 대기 상태이거나 취소가 아닌 종료 상태인 기록을 허용했습니다.
두 쓰기 경계는 이미 취소 우선 종료를 강제하고 완료 후 새 취소 의도의 기록을 거부합니다.
공통 스키마도 취소 의도가 있으면 실행 중 또는 취소됨 상태만 허용하도록 맞췄습니다.
수정 전에는 부정 사례 5개가 실패했고, 수정 후에도 정상 실행 중·취소 완료 이력은 허용합니다.
기존 합성 성공 fixture가 실행 중 fixture의 취소 정보를 잘못 물려받은 점도 바로잡았습니다.
저장된 데이터를 변경하거나 상태 전이 의미를 바꾸지 않았으며 결과 읽기 테스트도 취소를 무시한
성공 이력을 거부하는지 검사합니다.

[테스트](../../packages/replay/src/policy-evaluation-replay-result-reader.test.ts)는 기존 정의
벡터에서 실제 메모리 저장소의 대상·계획·작업 생성·claim·예산·관찰·완료 흐름을 실행합니다.
참조의 모든 말단 필드, 세 범위 차원, 성공하지 않은 모든 작업 상태, 과거 시도 대체,
미종료·중첩 이력, 손상 기록, 정밀 시각 경계, 성공 이력의 기록 시각 종류별 미래 값, JSON 표현 일치,
사본 격리, 입력 변경, 운영 오류와 정확한 개수·UTF-8 바이트 경계를 검사합니다.
해시는 독립적으로 정렬한 JSON 오라클과 비교합니다.

`verified`는 기록 관찰이지 정책 충족, 승인, 실행 증명, 제공자의 실제 행동이나 오래된 OS
프로세스 종료를 증명하지 않습니다. 저장소가 완전한 권위 이력을 반환한다는 신뢰가 필요합니다.
반환된 값을 해시한다고 누락된 이력 말미를 독립적으로 탐지할 수 있는 것은 아닙니다.
결과 참조에는 작업 이력 전체의 사전 해시가 없으며 새 해시는 이후 스냅샷 결속용 관찰입니다.

계획·대상·데이터셋·fixture·프로파일 및 아티팩트의 재귀 관계, 소유권·실제 바이트·출처 권한,
전체 충돌·의존 관계 검사, 보호된 봉인, 순수 규칙 평가, 영속 작업·별도 DB 역할,
API·SDK·워커, 실제 서비스 기반 기여자 실행과
[체크포인트 종료 조건](workflow-2-policy-evaluation-entry-audit.ko.md)은 계속 남아 있습니다.
새 DB 쓰기, capability, endpoint, 웹사이트나 고정 사용자용 포트는 추가하지 않습니다.
