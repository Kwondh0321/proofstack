# 권한을 확인한 정확한 아티팩트 관측

[English](workflow-2-policy-artifact-observation.md) |
[한국어](workflow-2-policy-artifact-observation.ko.md)

상태: 아티팩트 소유 도메인의 개별 콘텐츠 관측 구현. 후속
[요청 기반 수집](workflow-2-policy-artifact-capture.ko.md)이 이 검증기를 연결합니다. 경쟁 방어를
포함한 스냅샷 봉인과 Workflow 2의 세 번째 체크포인트는 아직 미완료입니다.

## 콘텐츠보다 먼저 권한 확인

`@proofstack/artifacts`의 `readPolicyEvaluationArtifact(input, dependencies)`는 기존 카탈로그,
오브젝트 저장소, 암호화, 서버 시계 포트로 정확한 콘텐츠 참조 하나를 관측합니다. 비동기 I/O
전에 범위, 인증된 주체, 원래 `ContentReference`, UTC 평가 시각과 호출별 암호문 읽기 한도를
검증하고 복사합니다. 내부 도메인 함수이며 새 HTTP 경로·공개 SDK·인증 제공자가 아닙니다.
호출자는 주체를 클라이언트 JSON이 아닌 신뢰된 인증 경계에서 받아야 합니다.

`artifact:read`, 프로젝트·환경 접근 권한과 주체의 테넌트 일치를 확인합니다. 제한된 콘텐츠
참조는 카탈로그 조회 전 `artifact:read:restricted`도 요구합니다. 저장된 실제 분류도 metadata
보존과 콘텐츠 조회 전에 다시 검사하므로 호출자가 분류를 낮춰 제출해 우회할 수 없습니다.
`policy:evaluate`, 참조·해시 또는 앞선 그래프 조회 자체는 원문 읽기 권한이 아닙니다.

원래 증거 참조가 관리형 `ArtifactContentReference` 계약 밖이면 저장소 조회 없이
`reference_unsupported`로 남깁니다. 크기 0과 관리되지 않는 media type을 임의 변환하거나
관리형 아티팩트가 있다고 만들어내지 않습니다.

## 고정 검증과 관측

카탈로그의 public·private 필드를 검사합니다. 엄격한 metadata, 생성자 ID, 제한된 저장 위치,
고정 암호화 버전, canonical 키 envelope 인코딩, 암호문 영수증과 선택적 fixture 소유권을
확인합니다. 범위·전체 콘텐츠 참조·소유권 식별자와 범위·접수 시각 순서가 맞아야 합니다.
시각은 오프셋과 소수점 이하 30자리를 보존하고 지원 범위를 넘으면 잘라내지 않고 거절합니다.
이 도메인 검사는 앞단에서 한도 있는 raw JSON을 승인한 저장소 응답을 전제로 하며 전송 파서,
getter 격리 장치나 프로세스 메모리 상한은 아닙니다.

서버 시계가 `startedAt`·`completedAt`을 정하고 평가 시각은 시작 이후일 수 없습니다. 유효하지
않거나 뒤로 움직이는 시계는 실패합니다. 생성·활성화는 평가 시각 이하여야 하고 보존된 이력이나
소유권 접수가 현재 관측 시각 이후일 수 없습니다. 현재 reserved·tombstoned·purged·만료 상태는
과거 평가 시각을 주어도 이용 불가입니다. 삭제된 과거 바이트를 복구한 척하지 않습니다. 만료
시각과 같거나 검증 도중 만료에 도달한 경우도 이용 불가입니다.

이용 가능한 정확한 기록은 복호화 전 암호문의 크기·SHA-256을 영수증과 비교합니다. 기존 인증
암호화를 사용한 뒤에도 반환 원문의 크기·SHA-256을 정확한 참조와 독립적으로 다시 확인합니다.
다른 오브젝트·URL·최신 버전·유리한 재시도 결과를 선택하지 않습니다. 반환값에 원문, 내부 저장
위치, 암호화 계획, 감싼 데이터 키나 주체 자격 정보를 포함하지 않습니다.

| 관측 | 근거 |
| --- | --- |
| `verified` | 암호문 영수증과 원문 크기·해시 검증, 두 번째 조회에서도 동일한 카탈로그 |
| `missing` | 정확한 권한 범위의 카탈로그가 null 반환. 오브젝트 조회 없음 |
| `reference_unsupported` | 원래 증거 참조가 관리형 아티팩트 계약 밖임 |
| `record_invalid` | 카탈로그 계약·암호화 설명·영수증·소유권·고정밀 시각 순서가 잘못됨 |
| `reference_mismatch` | 범위나 전체 참조 불일치. 다른 대상의 metadata는 보존하지 않음 |
| `not_yet_available` | 생성·활성화가 평가 이후이거나 보존된 접수가 서버 관측 시각 이후임 |
| `reserved`, `tombstoned`, `purged`, `retention_expired` | 현재 생명주기·보존 상태에 따른 이용 불가이며 카탈로그 부재는 아님 |
| `object_missing` | 이용 가능한 정확한 카탈로그에 대응하는 실제 오브젝트가 없음 |
| `content_integrity_failed` | 반환된 암호문·원문의 형태·크기·해시가 승인된 기록과 모순됨 |

`verified`·`missing`을 제외한 이유는 `status: unavailable`입니다. 정확하고 유효한 카탈로그
관측은 public metadata, 선택적 소유권과 원래 접수 필드를 포함한 전체 private 기록 해시를
보존합니다. 해시는 저장 위치나 키를 노출하지 않습니다. 소유권은 관측된 출처이지 정책 평가
시각에 그 소유자가 유효하거나 승인됐다는 판정은 아닙니다.

## 오류와 경쟁 상태는 별도 처리

카탈로그·오브젝트·키 제공자와 예상 밖 구현 실패는 그대로 전파합니다. 특히
`ArtifactProtectionError`는 알려진 손상이나 일반 부재로 바꾸지 않습니다. 기존 암호화 계층은
키 제공자 장애도 이 오류로 감싸므로 그 예외만으로 저장된 바이트의 변조를 증명할 수 없습니다.
후속 워커는 운영 실패를 완료된 indeterminate 평가로 몰래 변환하지 않아야 합니다.

오브젝트 응답과 필요한 복호화가 끝나면 같은 카탈로그를 다시 읽습니다. 오브젝트가 없거나
잘못된 응답이어도 확인합니다. 사라짐·잘못된 대체 기록·전체 기록 변경은
`PolicyEvaluationArtifactCaptureError`의 `source_revision_changed`로 실패합니다. 비교 해시는
public 콘텐츠 해시뿐 아니라 소유권·생명주기·저장 위치·암호화 계획·영수증도 포함합니다. 입력,
보존된 카탈로그와 포트 인자는 별도 복사하여 포트가 비교 기준을 바꾸지 못하게 합니다.

두 조회가 일치해도 DB 잠금, 원자적 오브젝트 snapshot, 중간 변화가 없었다는 증명 또는 조회
직후의 변경 방지는 아닙니다. 봉인 시점의 DB 트랜잭션에서 권한 있는 revision을 다시 검증해야
합니다. 이 함수는 재시도하거나 더 유리한 관측 시점을 선택하지 않습니다.

## 한도와 완료 경계

`maxReadBytes`는 호출별 암호문 상한으로 0부터 기존 16 MiB 콘텐츠 상한에 envelope 20바이트를
더한 값까지입니다. 조회 전 예상 암호문 크기가 들어가야 하고 응답을 복사·해시하기 전에도
길이를 확인합니다. 0은 필수 콘텐츠 검증 면제가 아닙니다. 성공·알려진 이용 불가 반환값은
카탈로그 호출 수·오브젝트 호출 수·수신한 오브젝트 바이트를 기록합니다. 요청 전체의
`maxArtifactReadBytes` 장부, 부분 전송·HTTP 재시도 비용, 취소 또는 스트리밍 메모리 상한은
아닙니다. 후속 조립·워커는 포트와 실패를 누적 계측해야 하며 성공 결과만 합산하면 안 됩니다.

실제 메모리 저장소·인증 암호화와 적대적 포트 응답을 사용해 권한 거절, 엄격한 계약, 전체 기록
해시, 고정밀 시각, 생명주기·만료, 바이트 상한, 암호문·원문 모순, 키·저장소 실패, 입력·인자
변경과 I/O 중 카탈로그 변경을 검사합니다. PostgreSQL 정책 워커나 출시 종단 간 검증은
아닙니다. 기존 아티팩트 읽기 경로·암호화 계약·생명주기 전이는 변경하지 않습니다.

후속 [아티팩트 수집](workflow-2-policy-artifact-capture.ko.md)이 그래프·트레이스 출현을 공유
메타데이터 한도와 보수적 오브젝트 예약으로 연결합니다. 예상 소유권·전체 의미 관계, 변경
가능한 권한·트랜잭션 경쟁 방어는 남아 있습니다. 이후 snapshot 봉인, 정책 조건, 영속 작업·
API/SDK·복구·격리·종단 간 검증이 이어집니다. Workflow 2의 완료 수는 7개 중 2개로 유지합니다.
