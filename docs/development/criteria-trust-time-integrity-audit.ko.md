# 기준 신뢰 유효 기간의 시각 정밀도 검토

[English](criteria-trust-time-integrity-audit.md) | [한국어](criteria-trust-time-integrity-audit.ko.md)

검토일: 2026-10-03. 범위: `evaluateCriteriaTrust`의 의미적 유효 기간 비교.
이 수정은 과거 Workflow 1 감사를 대체하거나 Workflow 2를 완료 처리하지 않습니다.

기존 검사는 PostgreSQL 커서 순서에 맞추려고 소수 초를 마이크로초로 반올림하는
`evidenceTimestampOrderKey`를 사용했습니다. 그러나 보존된 유효 기간은 그보다 정밀한 시각을
허용합니다. 평가 시각 자체가 밀리초여도 오류가 발생합니다.

평가 시각 `2026-09-02T00:01:00.000Z`보다 `2026-09-02T00:01:00.0000004Z`는
0.4마이크로초 뒤이지만 기존 커서 키는 같았습니다. 나머지 조건이 적격인 픽스처의 정확한
참조와 해시를 다시 구성하여 다음 두 오류를 재현했습니다.

- 미래 시각에 효력이 생기는 출처가 `source_not_effective` 사유 없이 `eligible`로 판정됨.
- 미래 시각에 만료되는 출처가 이미 `source_not_current`로 판정됨.

기준 상태, 출처 검토, 검토자 자격, 평가자·oracle 자격의 유효 기간에서도 같은 오류를 확인했습니다.
기존 소유 픽스처를 이용한 순수 메모리 검사이며, 실제 PostgreSQL이 서브마이크로초 값을 저장했거나
운영 출시에서 이 값을 사용했다는 주장은 아닙니다.

의미 비교는 이제 `policyEvaluationTimestampOrderKey`로 지원되는 소수 30자리와 UTC 오프셋을
정수 연산으로 보존합니다. 효력·유효 시작은 포함하고 만료·유효 종료는 제외합니다. 원문 시각과
해시를 다시 쓰지 않으며 DB 커서의 반올림 동작도 유지합니다. 기존 신뢰 API의 밀리초
`at`·`evaluatedAt` 계약, 서버 소유 기록과 실제 파일 가용성 요구는 그대로입니다.
새 시간 선택 권한·경로·역할·DB 마이그레이션은 추가하지 않았습니다. 후속 정책 평가 연결은
별도의 정밀 시각 계약을 보존해야 하며 이 API에 맞춰 반올림해서는 안 됩니다.

추가한 60개 사례는 다섯 권한 주체, 시작·종료 경계, 평가 직전·동일·직후 시각, 동등한 UTC 오프셋,
0.4마이크로초 차이와 마지막 지원 소수 자리를 검사합니다. 기대 순서는 명시적으로 지정하여
제품의 시간 키 함수를 테스트 정답 생성에 사용하지 않습니다. 픽스처의 참조·해시는 일관되게
갱신하고 원래 입력은 유지합니다. 기존 규칙을 포함한 해당 파일의 89개 테스트가 통과했습니다.
커버리지 기준과 공개 접수 시각 스키마는 유지하며 전체 저장소·정확한 커밋 CI 검사도 필요합니다.

`eligible`은 보존된 구조적 권한 전제조건의 결과입니다. 출처의 사실성, 현재 논리 루트 등록,
참조되지 않은 변경 이력의 완결성, 실제 실행, 입력 봉인, 인간 승인이나 출시 권한은 별도입니다.
전체 정책 출처 closure와 Workflow 2 checkpoint 3의 나머지 작업은 미완료입니다.
